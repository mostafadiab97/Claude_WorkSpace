Saved by the builder: the helper answered in its message. Script: `tools/perf-qa-trace.mjs` (`node --import tsx tools/perf-qa-trace.mjs <repo>`, `SKIP_EXPORT=1` skips the exports).

Scope: in-process measurements on generated scenario repositories with the starter rules (6 rules). One repository existed at a time: 10,005 items, then 50,004. Both are deleted. The new script is `/home/claude/claude_workspace/tools/perf-qa-trace.mjs`. Run it with `node --import tsx tools/perf-qa-trace.mjs <repo>`. Set `SKIP_EXPORT=1` to skip the big exports. **Findings**

| ID | file:line | Severity | What is wrong (F = checked, I = likely) | Suggested fix |
| --- | --- | --- | --- | --- |
| P1 | `traceability.ts:115-126` and `xlsx.ts:55-61` | High | F: The matrix export builds a full dense grid of empty strings, one row per row item and one column per linked item. It then adds every row to ExcelJS. At 10k it takes 9 to 10 s and writes 5 MB, with only 1,320 filled cells out of about 2 million. At 50k (8,230 × 1,503 ≈ 12 million cells) the process ran out of its 2 GB heap and crashed. In the app this would hit the main process. Even an 84-row export takes 3.5 s and 2 MB. | Write only the filled cells. Cap the export, or switch to a list format (row, column, link type). Stream rows or use ExcelJS's streaming writer. Warn before a large export. |
| P2 | `traceability.ts:46` and `xlsx.ts` | Medium | I: Column count equals the number of distinct linked items. Excel allows at most 16,384 columns. A large project can exceed that, and the file would be invalid or truncated. I did not test this. | Cap columns, or fall back to a list format. |
| P3 | `WorkspaceScreen.tsx:317`, `sqliteIndex.ts:439` | Medium | F: Gaps count (limit 0) takes 340 ms at 50k and 33 ms at 10k, about 10 times for 5 times the items, so it grows worse than linearly. Even `limit 100` costs 505 ms, so the cost is the gap SQL itself (an OR of 6 NOT EXISTS subqueries), not the paging. The window runs it on every data change, so each save probably adds about 0.35 s of background work at 50k. | Add an index on link target and type, or cache the count per data version. Compute it only when the status bar is visible. |
| P4 | `sqliteIndex.ts:536-544`, `traceability.ts:53-60` | Medium | F: getCoverage sends every gap item with its title to the window. That is 587 KB at 10k and 3 MB at 50k (27,815 gaps). It is synchronous on the main process: 380 ms at 50k, over the 300 ms query limit. | Return counts plus the first N gaps per rule, and page the rest on demand. |
| P5 | gaps query with `limit 10000` | Medium | F: Paged 10,000 gap rows take 884 ms at 50k. At 10k the same query takes 170 ms, over the 150 ms limit. | Page smaller. Make the gaps SQL faster (see P3). |
| P6 | `traceability.ts:64-98` | Low | F: Impact of a top heading hits the 5,000-node cap at 50k, sends a 1 MB payload and takes 406 ms. It runs one `queryAll` per parent. The cap makes the cost bounded, but the result is incomplete (flagged by `truncated`). | Fetch children in batches. Keep the cap. |
| P7 | `traceability.ts:24-50` | Low | F: `getMatrix` builds the full matrix (all rows and cells) and then cuts it to 2,000 rows. At 50k that costs 463 to 753 ms for a view of 2,000 rows. | Cut the rows before building the cells. |
| P8 | `schemaFields.ts:55-67` | Low | F: `saveSchemaRules` reopens the repository and re-syncs. It takes 780 ms at 50k, which is acceptable. It runs on the workspace queue, so other writes wait behind it. | None needed. |
| P9 | `queryItems` limit | Low | F: `queryItems` limits to 10,000 rows per page, so any caller assuming "all items" in one call at 50k gets a partial list. My own script hit this and had to page. | Document the limit in the `ReqochetApi` comment. |

**Questions for the owner:** Is a matrix Excel export of more than about 2,000 rows needed? If not, a cap with a notice is the simplest fix.

**Checked, nothing found:** the coverage rules schema round trip (`saveSchemaRules` result `ok`), and impact on a leaf item (0.1 ms).
