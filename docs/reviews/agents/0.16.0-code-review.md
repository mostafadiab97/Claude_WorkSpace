## Findings

### CR-01 — Medium — The settings move deletes `%APPDATA%\ReqMan` even when copying failed, and a later start deletes it without copying

`src/main/legacyData.ts:31-48`

Evidence: a failed `cp` is only logged (line 43). The marker is still written (line 46) and the old folder is removed
(line 48). On the next start the marker (or a `theme.json` / `recent-repositories.json`) leads to the "already moved"
branch (line 32), which removes the old folder **without copying anything**. Two ways this loses the user's files:

1. A copy fails (`EBUSY`/`EPERM`: an old ReqMan still running, a virus scanner, OneDrive-redirected AppData, a long
   path). `rm` then fails on the same lock, so the folder survives the first start. The second start deletes it
   because the marker is there. Lost: whatever was not copied. That includes the import memory (`imports/`). Without it,
   re-importing the same Excel/ReqIF file creates duplicate items instead of updating them.
2. If ReqMan is still installed (the uninstaller in CR-02 failed, or the user reinstalled it) and the user keeps using
   it, every later reqochet start deletes ReqMan's new settings and import memory.

Fix: remove the old folder only in the same run that copied everything without error (`copied.length === kept.length`).
On later starts, remove it only if nothing in it is newer than the marker. Otherwise keep it and log. Add unit tests:
copy fails on one entry, then the old folder is kept; an old folder changed after the marker is kept.

### CR-02 — Medium — The installer force-kills a running ReqMan, so unsaved edits are lost without the usual question

`build/installer.nsh:10`

Evidence: `taskkill /IM ReqMan.exe /F` ends the process at once. ReqMan's "You have unsaved changes" dialog
(`src/main/index.ts` close handler) never runs. If the owner (or a colleague) downloads `reqochet-dev-Setup-0.16.0.exe`
and runs it while ReqMan is open with an item being edited, the typing is lost. A forced kill during a Git command
(commit, pull) can also leave `.git/index.lock` behind, and then every Git action fails until someone deletes it by
hand. During auto-update this is harmless, because ReqMan has already quit. The manual install is the case at risk.

Fix: in non-silent mode, if `ReqMan.exe` is running, show a message box ("Close ReqMan first, then click Retry") and
loop, as electron-builder's own `CHECK_APP_RUNNING` does. In silent mode, first send a normal `taskkill /IM ReqMan.exe`
(without `/F`, so the window gets a close request), wait a few seconds, and only then use `/F`.

### CR-03 — Medium — "Update this project" commits uncommitted and untracked files of the project folder under a rename message

`src/modules/workspace/workspace.ts:108-110`, `src/modules/git-adapter/systemGit.ts:260-263`

Evidence: `commitFiles` runs `git add -- requirements/.reqman requirements/.reqochet`, then `git commit --only` on the
same paths. Both cover the whole folder. Reproduced in a scratch repository: an uncommitted edit to `schema.yaml` and a
new untracked file in `.reqman` both end up in the commit
`requirements/{.reqman => .reqochet}/schema.yaml | 1 +` and `requirements/.reqochet/notes.txt | 1 +`, under
"Rename the project folder .reqman to .reqochet". The user sees one commit ready to push and does not expect field
changes in it. The test `"Update this project" … nothing else is committed` uses a clean folder only.

Fix: before renaming, check `git status` for `requirements/.reqman` and refuse with a clear message ("commit or discard
your field changes first") when it is not clean. Or use `git mv` (`git mv requirements/.reqman requirements/.reqochet`),
then `git commit --only` with only the paths Git tracked. Add a test with an uncommitted schema edit.

### CR-04 — Medium — If the rename commit fails, the folder stays renamed but the open session still points at `.reqman`

`src/modules/workspace/workspace.ts:105-118`

Evidence: the disk rename runs first (line 108), then the commit (line 110). If the commit throws, the `catch` returns
`{ ok: false }` without re-opening the repository. The session keeps `s.repo` (its `schemaFile` closure points at
`.reqman/schema.yaml`, which is now gone) and a watcher on the removed folder. Reproduced: a project whose `.reqman` was
never committed (a new project not yet committed, or created before the first commit) makes `git add -- requirements/.reqman`
fail with `fatal: pathspec 'requirements/.reqman' did not match any files`. Other causes: a missing Git identity, a
commit hook. After that, saving fields fails (ENOENT on the old schema path). Clicking "Update" again gets `null` from
`renameLegacyFolder` and returns `ok: true` with the stale `info()`, so the banner never goes away until the repository
is reopened.

Fix: pass only the paths Git knows (or use `git mv` / `git add -A -- requirements/.reqochet` plus `git rm -r --cached`
for the old path only when it is tracked). On any error after the disk rename, either rename back or re-open the
repository and recreate the watcher in a `finally`. If `renameLegacyFolder` returns `null`, still re-open the repository.
Add a test for "not yet committed" and one for a failing commit (for example, no identity).

### CR-05 — Low — After a pull or branch switch that renames the folder, the watcher keeps watching the old folder name

`src/modules/workspace/workspace.ts:80-85` (`resyncAll`), `src/modules/workspace/workspace.ts:195-203` (`refresh`)

Evidence: the watcher gets the folder name once, at `open` and in `renameProjectFolder`. When a colleague's rename
arrives by pull (or the user switches between a renamed branch and an old one), `resyncAll` re-opens the repository
with the new `metaDir` but keeps the old watcher. `.reqochet/schema.yaml` is then not watched, so a schema edited in an
editor (or by a later Git action that does not resync) is not picked up until the repository is reopened. The window
then works on old field definitions. It is not data loss, because schema saves are conflict-checked.

Fix: in `resyncAll` and in the full branch of `refresh`, recreate the watcher when `repo.metaDir !== s.repo.metaDir`.
A simpler alternative: watch both names (or the `requirements` folder itself) for `schema.yaml`.

### CR-06 — Low — The Fields dialog still shows `requirements/.reqman/schema.yaml`

`src/renderer/src/workspace/FieldsPanel.tsx:268`

Evidence: the path is a literal in the dialog intro. For every new project, and for every renamed one, the window
names a folder that does not exist. It also contradicts the user guide.

Fix: build it from the repository (`info.legacyFolder ? '.reqman' : '.reqochet'`). Also update the comments that
still say `.reqman` (`src/shared/domain.ts:4`, `src/modules/schema/index.ts:3`, `src/shared/features.ts:2`,
`src/modules/repository-store/index.ts:7`, `src/modules/workspace/watcher.ts:9`).

### CR-07 — Low — The switch leaves ReqMan's update cache behind (`%LOCALAPPDATA%\reqman-updater`)

`src/main/legacyData.ts`, `build/installer.nsh`

Evidence: the 0.15.2 updater downloaded the about 100 MB 0.16.0 installer into `%LOCALAPPDATA%\reqman-updater\pending`.
Nothing removes it, and the new app uses `reqochet-dev-updater`. This goes against the decision "a clean switch: no
files left under the old name".

Fix: in `moveLegacyUserData` (the app's first start, when the installer has already finished), also remove
`join(app.getPath('home'), 'AppData', 'Local', 'reqman-updater')`, or `%LOCALAPPDATA%` from `process.env`. Do not
remove it in `customInit`, because during auto-update the running installer lives there.

### CR-08 — Low — The installer deletes the ReqMan folder even when the ReqMan uninstaller failed

`build/installer.nsh:11-12`

Evidence: the exit code of `ExecWait` is not checked, and `RMDir /r` runs anyway. If the uninstaller fails (cancelled,
blocked), its registry entry and Start-menu or desktop shortcuts stay behind. They point to a deleted folder, and
"Apps → ReqMan → Uninstall" then fails, because the uninstaller is gone too.

Fix: `ExecWait '…' $0`, and run `RMDir /r` only when `$0 == 0`. Otherwise leave the folder so Windows can still
uninstall ReqMan, and log it (`DetailPrint`).

### CR-09 — Low — The old ReqMan logs are deleted with the old folder, just when the switch might need them

`src/main/legacyData.ts:7-10`

Evidence: `logs/` is not in `KEEP_DIRS`, and the folder is removed. If something about the switch goes wrong (an
update error in 0.15.2's last run, a failed copy), "Report a problem" in the new app only has `reqochet.log` /
`reqochet.old.log`. The evidence is gone.

Fix: copy the last ReqMan log into the new logs folder as `reqman-last.log` (the problem report can attach it), or
keep `logs/` once.

### CR-10 — Low — The new error message for two project folders is English only

`src/modules/repository-store/fileStore.ts:250` (`renameLegacyFolder`), shown by `WorkspaceScreen.renameFolder` as
a notice

Evidence: `Both .reqman and .reqochet exist in requirements; keep one.` is a literal. CLAUDE.md S-06 says core
messages shown to the user come from `src/shared/text.ts` (with Arabic). The Arabic window would show English here.

Fix: return a code (or throw a typed error) and map it to `T.wsMsg.bothFolders` in workspace.ts, with the Arabic key.

## Missing tests (summary)

- `legacyData`: a copy fails partway (CR-01); an old folder changed after the marker; the call when `newDir` does not
  exist yet.
- `renameProjectFolder`: uncommitted schema edit (CR-03); `.reqman` never committed or the commit fails (CR-04); a second
  click after a failure.
- Watcher after a folder rename that arrives by pull (CR-05).
- The acceptance run covers only the auto-update path. The manual install over a *running* ReqMan (CR-02) is not
  tested anywhere. Consider one more acceptance step: start 0.15.2, then run the new installer `/S`, and check that the
  old app is gone and the new one starts.
