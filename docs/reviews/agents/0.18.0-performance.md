# Performance report — 0.18.0 (frozen commit 2653a2a)

Scope: the data-layer and Git cost of the 0.18.0 features at 10,005 and 50,000 generated items (10 document folders,
301 commits, one baseline tag): the new top-level query for one document (`NOT EXISTS` parent in the same document, CASE
expression), the table's Incomplete-IDs query (limit 10,000, run on every data change), `getSnapshot` of an old commit,
history paging with `--grep`, `gitState` with the cached pending baselines, `renewCopyId`, and discarding many files with
the empty-folder removal. Method: new scripts in `/tmp/claude-0/perf-0.18/` (`perf-qa-0.18.mjs <workdir> <count>` is the
main one; `snap-prof.mjs`, `disc-prof2.mjs`, `incomplete.mjs`, `incpages.mjs`, `rmdir-test.mjs` are the profiling
helpers; the builder may copy the main one to `tools/perf-qa-0.18.mjs` and change its imports to `../src/...`). They
build a Git repository, run the real `createWorkspace` for the Git parts and the index directly for the queries (median
of 3–7 runs). Linux container, Node 22, Git 2.43, SQLite 3.53; the window (IPC, rendering) was not measured, only the
cost of copying the result (`structuredClone`, what Electron does). Windows process start-up (slower than Linux) is not
included, so every Git-heavy time below is a lower bound there. No product file was changed.

Targets: query < 150 ms at 10k and < 300 ms at 50k (`tests/perf.test.ts`); the owner's 10k "< 15 ms" in
`docs/TESTING.md`. For Git actions there is no written target; I treat > 1 s as "feels slow" and > 5 s as "looks hung".

| PERF-01 | `src/modules/git-adapter/systemGit.ts:697-705` | Medium | F: The empty-folder removal after a discard is **quadratic in the number of folders**. After each `rmdir` the loop climbs to the parent (`requirements/`) and calls `readdir` on it, which lists every remaining sibling folder. Measured through `git.discard` (10,000 new files, one per folder): **33.7 s at 10k, 37.9 s at 50k** (31.7 s of it the folder loop; the same loop alone in a plain Node test: 2,000 folders 1.3 s, 10,000 folders 26.4 s). With 2,000 folders: 3.3 s (10k) / 5.4 s (50k) in total. The whole app waits in the workspace queue meanwhile. Few document folders is the normal case, so this bites only a discard of many new folders (a big import into many documents, a copied project) — but the time is unbounded and a trivial change removes it. | Do not `readdir` at all: collect every ancestor folder of the removed files up to (not including) the requirements folder, sort deepest first and call `rmdir` once each, ignoring `ENOTEMPTY`/`ENOENT` (`rmdir` refuses a non-empty folder). Measured on the same shape: 2,000 folders 1.3 s → 0.15 s; 10,000 folders 26.4 s → 1.2 s. Add a unit test with a few hundred folders. |
| PERF-02 | `src/modules/workspace/baselines.ts:68-109` | Medium | F: `getSnapshot` costs **2.6–3.0 s at 10k and 8.3–8.8 s at 50k** (a repeat of the same commit costs the same: no cache). The result is then sent whole to the window: 3.9 MB JSON at 10k (copy 85 ms), **19.6 MB at 50k (copy 298 ms)**. (2) Yield to the event loop every ~500 items (`await new Promise(setImmediate)`) so the window stays alive. (3) I: parse only what the table needs (id, title, type, parent, order, number) and fetch text/fields/links of the selected item on demand, which also cuts the 19.6 MB copy. |
| PERF-03 | `src/renderer/src/workspace/ItemTable.tsx:70-76`, `src/modules/index-cache/sqliteIndex.ts:383-398,474-480` | Medium | F: The Incomplete-IDs loop runs on every `dataVersion` change and asks for **full brief item rows** although only `id` is used. Also do not refetch on every data change if the saved item's required fields did not change (the window knows the item it saved). |

## Questions for the owner

None — the findings are technical.

## Checked, nothing found

- The new top-level query for one document (parent in the same document via `NOT EXISTS`): within target at 10k and 50k, no sort of the whole table needed for the first page, deep offset 21 ms at 50k; faster than 0.17 at 50k.
- All-documents order with the CASE expression: unchanged from 0.17 (7 ms / 39 ms).
- `gitState` with the cached pending baselines: no extra Git process on refresh; 39 / 75 ms warm.
- `renewCopyId`: 37 / 55 ms including the tracked-file list and re-sync; it does not grow with the item count in a way that matters.
- `listBaselines` and the baseline tag read: ~10 ms at both sizes.
- Not measured: the window (rendering the snapshot table, the history dialog while typing), Windows Git start-up and Defender effects, the effect of the Incomplete mark rendering, history with thousands of commits (only 301 built), the file watch during a large discard.
