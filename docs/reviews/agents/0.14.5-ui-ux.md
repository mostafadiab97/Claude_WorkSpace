# UI/UX review — 3 Nov 2026

Version reviewed: 0.14.5 (29 screenshots, user guide, `config/theme.json`, `styles.css` for token usage). Behaviour that
is not visible in a screenshot is marked "inferred".

## Summary

ReqMan already looks like a calm, conventional engineering tool: one table, one editor, a status bar, few colours, and
the Git work is surfaced in plain words ("Get what others pushed first?", "Keep yours / Take theirs"). The structure
is right for all-day use; most problems are about layering, readability of the main table, accessibility contrast and
right-to-left text handling, not about the concept. The three most important problems are: (1) the floating Git
note stays on top of dialogs and pop-ups, so a push question can sit over the Export dialog and the branch panel
(UX-01); (2) in Arabic, Latin user content (titles, text, parent) is laid out right-to-left, so titles are cut off at
the wrong end and punctuation jumps to the wrong side (UX-02); (3) the table hides the information users scan for —
titles, types and even outline numbers are cut off, while the ID column takes the most visible place (UX-03, UX-04).
The success green (`success`, about 2.3:1 on white) and the focus ring (`focus`, about 2.5:1) fail WCAG 2.2 AA (UX-05,
UX-06). Three quick wins: darken `success`, `warning` and `focus` in the light theme (UX-05, UX-06), give user-content
elements `dir="auto"` (UX-02) and fix the broken releases link in the built-in guide (UX-12). A DOORS/Jama user will
mostly miss a readable "document" view with rendered text and visible keyboard shortcuts, and will stumble over the
cryptic links column (`→1 ←3`).

## Findings

### UX-01 Floating Git note sits on top of dialogs and pop-ups
- **Screen / element:** 13-floating-git-note, 14-branch-panel, 15-export-dialog — the push question note under the top bar.
- **Problem:** The note is above everything: the modal backdrop of Export does not dim it, and the branch panel opens partly underneath it. A user can click "Push without pulling" while another dialog is open, or cannot read the branch panel; two questions compete.
- **Evidence:** In 15 the Export dialog is dimmed-modal but the note "Get what others pushed first?" with its blue "Pull first, then push" stays bright and clickable. In 14 the branch panel's right half is covered by the note ("…shed first?").
- **Proposal:** (a) A note that asks a question (has action buttons) is a small anchored dialog, not a floating note: show it as a pop-over under the Push button (same component as the switch-branch question in 28), modal to the top bar only, closed by Esc. (b) Plain result notes (done / problem / nothing to do) keep floating but sit below modal dialogs and pop-overs in the stacking order: layers `toast` < `popover` < `modal-backdrop` < `modal`. (c) Opening any pop-over or dialog closes a pending question note (treated as "Cancel"). Floating notes never cover the top-bar buttons that triggered them: anchor them to the start of the content area, below the toolbar.
- **Severity:** High
- **Effort:** M
- **Type:** Interaction

### UX-02 Arabic: Latin user content is laid out right-to-left (cut at the wrong end, punctuation jumps)
- **Screen / element:** 18-arabic-rtl — table Title/Type cells, editor Text, Parent, Links row.
- **Problem:** User content written in English inherits the window's RTL direction. Titles are truncated at their beginning ("…vice detects access tokens"), so the meaningful start is lost; sentence punctuation and Markdown markers move to the wrong side (".power Loss", "Rationale:** … in**"); the parent reads "REQ-38X44C6 — … tokens 2.1.1". Most pilot content will be English even for Arabic-UI users.
- **Evidence:** Title column cells start with "…"; Type shows "… / Information"; the Text area shows ".power Loss" and "all supported languages." with the full stop at the start.
- **Proposal:** Give every element that shows user content (table cells for title, type, owner, tags, text; editor inputs and textarea; parent field; link titles; Changes rows; diff lines; problem list) `dir="auto"` (inputs/textarea) or `unicode-bidi: plaintext` (cells), so direction follows the first strong character of the content. Keep `text-align: start` so the column alignment still follows the window. Truncation then cuts the end of the Latin text. Add an e2e check in the `language` scenario: an English title in Arabic mode has its ellipsis at the visual right.
- **Severity:** High
- **Effort:** S
- **Type:** RTL

### UX-03 Main table cuts off titles and types; Text column off-screen
- **Screen / element:** 02, 03, 07, 17 — tree table at 1600 px with the editor open.
- **Problem:** The title is the most important thing to read, but it gets about 245 px and is cut at ~30 characters ("Login screen notifys the …"), while ID (mono, 130 px) and No. (90 px) come first. Type is cut ("System Requi…", "Heading / Info…") so similar types (System / Software / Hardware Requirement) cannot be told apart. With the editor open the table scrolls sideways and Text is hidden.
- **Evidence:** 03: nearly every title ends in "…"; Type always truncated; horizontal scrollbar at the bottom; Text column not visible.
- **Proposal:** (1) Default column order: No., Title, Type, Status, Links, Priority, Owner, Tags, ID, Text (ID stays always visible but moves after the descriptive columns; users can reorder as today). (2) Title column takes the remaining width (flex), minimum 280 px; other columns get default widths sized to typical content (Status 96 px, Priority 80 px, Links 72 px). (3) Type shows a short label from the schema (new optional `short:` per item type, e.g. "SysReq", "SwReq", "HwReq", "Heading") with the full name in a tooltip; if no short label, the full name. (4) For heading rows (type Heading / Information) leave the Type cell empty and show the title in `--rm-font-weight-strong`; headings are recognised by weight, as in DOORS. (5) Full title in a tooltip after 600 ms hover on a truncated cell. (6) The table never needs a horizontal scrollbar for the default columns at 1366 px with the editor open: the editor gets a draggable splitter (min 360 px, default 32 % of the window, remembered on this PC).
- **Severity:** High
- **Effort:** M
- **Type:** Layout

### UX-04 Outline numbers are truncated in search results
- **Screen / element:** 07-search-results, No. column.
- **Problem:** "8.2.178…." and "8.2.200…." — the outline number itself is cut. A truncated number is a wrong number; users copy and quote these.
- **Evidence:** Rows REQ-2YFH6VN, REQ-R0TFAPG, REQ-RS8CWHV, REQ-CRF0H1F, REQ-ER99C9D show "…" in No.
- **Proposal:** The No. column never truncates: its width is computed from the longest visible number (`ch` units of the mono font + `--rm-space-md` padding) with a minimum of 64 px; show numbers in `--rm-font-family-mono` with tabular figures so columns of numbers align.
- **Severity:** Medium
- **Effort:** S
- **Type:** Layout

### UX-05 Success and warning colours fail text contrast in the light theme
- **Screen / element:** status bar "No problems" (25–29), import check "new" and "No problems found." (27), status dots in Settings (19), Changes warning "4 items link here" and suspect hint bar (12), "⚠ changed" (11).
- **Problem:** `success` #22c55e on white is about 2.3:1 (AA needs 4.5:1 for text). `warning` #b26b00 is about 4.2:1 on white and lower on the tinted hint bar in 12. Users with low vision or on a bright office screen miss these states.
- **Evidence:** 27: the green "new" words and "No problems found." are pale; 12: amber text on amber-tinted bar.
- **Proposal:** Light theme: `success` → #15803d (≈5.0:1 on white), `warning` → #8f5600 (≈5.6:1 on white, ≥4.5:1 on its tint). If the bright green is wanted for dots/frames, add `successStrong` for fills and keep `success` for text. Add a contrast test next to the hex test: every text token pair (text/textMuted/primary/success/warning/danger on background/surface/surfaceAlt) must reach 4.5:1 in both modes.
- **Severity:** High
- **Effort:** S
- **Type:** Accessibility

### UX-06 Focus indicator too faint; inputs remove the outline
- **Screen / element:** all screens; `styles.css` `:focus-visible` uses `--rm-color-focus`; `.input:focus { outline: none; border-color: focus }`.
- **Problem:** `focus` #7aa2ff on white is about 2.5:1 (WCAG 2.2 needs 3:1 for focus indicators), and on inputs focus is only a 1 px border colour change — keyboard users lose their place in a dense form and a 9,000-row table.
- **Evidence:** 03/12: the focused fields (e.g. search box with blue outline in 07) are barely distinguishable from unfocused ones; the selected table row uses `selection` #e3ebff, which is about 1.2:1 against white rows.
- **Proposal:** Light `focus` → #3866e0 (≈5:1). New token `focusWidth: 2px`. Inputs: keep the border and add `box-shadow: 0 0 0 var(--rm-shape-focus-width) var(--rm-color-focus)` on `:focus-visible`. Table: the keyboard-current row gets an inset 2 px focus outline in addition to `selection`; the selected row also gets a 3 px start-side bar in `primary` so selection does not depend on a faint tint. Dark mode keeps #9db8ff (passes).
- **Severity:** High
- **Effort:** S
- **Type:** Accessibility

### UX-07 One-click "Unlink all 4 suspect" is a plain text link
- **Screen / element:** 10-suspect-links-dialog — editor Links header: "Keep all 4 suspect  Unlink all 4 suspect  + Add link".
- **Problem:** A bulk destructive action (removing four trace links) is styled like a harmless hyperlink, placed right next to "Keep all" and "+ Add link". A mis-click silently changes four other items' trace (inferred: no confirmation visible). Wording "Keep all 4 suspect" is also not a full phrase.
- **Evidence:** Two blue text links at the same weight as "+ Add link" in the Links header.
- **Proposal:** Replace both with one small button "Check 4 suspect links…" (secondary style, `warning` icon ⚠ at start) that opens the existing "Check the links to this item" dialog, where Keep all / Unlink all already exist with clear context. If a direct bulk unlink is kept, it is a `danger`-outlined button and asks "Unlink 4 items from this item? They are not deleted." with Unlink / Cancel.
- **Severity:** High
- **Effort:** S
- **Type:** Interaction

### UX-08 Item text shows raw Markdown in the editor
- **Screen / element:** 03, 09, 11 — Text field.
- **Problem:** Engineers read "**Rationale:**", "**Objective:**", "- Measured on…" with literal asterisks and backticks. DOORS/Jama users expect formatted text; reading a long test case with Markdown markers is tiring and looks unfinished. (Rich-text editing is planned for theme 3a; this is the interim.)
- **Evidence:** 11: "**Objective:** verify…", "**Preconditions**", "**Steps**" shown raw; 09: backticks around a path.
- **Proposal:** Until 3a: the Text field shows rendered Markdown (same renderer as the user guide) when not focused; clicking into it or pressing Enter switches to the plain textarea; a small "Preview / Edit" toggle at the end of the "Text" label. The table's Text column shows the plain text without markers (strip `**`, `` ` ``, leading `- `).
- **Severity:** High
- **Effort:** M
- **Type:** Visual

### UX-09 Unsaved-changes guard is a small pop-over over the Save button, without "Save"
- **Screen / element:** 29-unsaved-changes-guard.
- **Problem:** The question covers the editor footer including part of Save, offers only "Discard changes" (red, first) and "Keep editing". The most common wish — save and continue — needs three clicks; the destructive option is the visually strongest.
- **Evidence:** Pop-over with an amber frame overlapping Save, "Discard changes" filled `danger`.
- **Proposal:** Show the guard as a centred small dialog: title "Save your changes to REQ-7YWMB0S?", buttons in this order (start → end): "Save and continue" (primary, default, Enter), "Discard changes" (danger-outlined, not filled), "Keep editing" (secondary, Esc). Same pattern for every "leave with unsaved changes" case (row change, close repository, switch branch).
- **Severity:** Medium
- **Effort:** S
- **Type:** Interaction

### UX-10 Links column notation is cryptic
- **Screen / element:** 03, 07, 11 — Links column ("→1 ←3", "→2 ⚠1"), and 18 (mirrored "3← 1→").
- **Problem:** New users do not know that → means "this item links to" and ← "is linked from"; DOORS users think in in-links/out-links. In Arabic the arrows keep their direction while their order flips, which reverses the meaning visually.
- **Evidence:** Header "Links" only; no legend visible; 18 shows "3← 1→".
- **Proposal:** Tooltip on each cell: "Links out: 1 · Links in: 3 · Suspect: 1". Header tooltip: "→ links from this item · ← links to this item · ⚠ suspect". In RTL, render the cell with `dir="ltr"` as a unit (arrows are a notation, not text) so it reads identically in both languages. Filters → Links offers "Has no links out", "Has no links in", "Has suspect links".
- **Severity:** Medium
- **Effort:** S
- **Type:** Wording

### UX-11 Problems panel is an undifferentiated list

Each row: item ID (mono), short message, and an action button at end when a fix exists ("Fix file name", "Remove link…"); per group "Fix all…" where safe. Severity icon (error ✕ in `danger`, warning ⚠ in `warning`) at start — not colour only. Status bar text: "19 problems" in `danger` only when at least one is an error, otherwise `warning`.
- **Severity:** Medium
- **Effort:** M
- **Type:** Layout

### UX-13 Top bar mixes rare preferences with daily Git actions
- **Screen / element:** 02–17 — top bar end: Changes, Pull, Push, English/العربية, Light/Dark/System, ⚙.
- **Problem:** Two segmented controls used once per install take the most prominent place and visually outweigh the Git buttons, which are small, neutral and equal. The Git counts "↑0 ↓0" sit next to the branch name, far from Push/Pull, and are not explained.

### UX-14 Editor footer: unlabeled move arrows, a select used as a button, small targets

### UX-15 Save state is hard to read (disabled vs. "Saved ✓")

New token `disabledOpacity: 0.5` used consistently for all disabled buttons instead of per-component pale colours.

- **Effort:** S
- **Type:** Visual

- **Problem:** Parent shows "2.1.1 REQ-38X44C6 — …" in an input-like box, so users try to type in it (inferred: it opens a picker). Tags takes half a row with nothing beside it; Owner is free text although teams have a fixed list.
- **Evidence:** Parent field identical to text inputs; empty half-row next to Tags.
- **Proposal:** Parent is a button-styled field with a trailing "Change…" label and the parent's number/title as a link that selects the parent in the table. Layout: Type | Status, Priority | Owner, Tags (full width), Parent (full width). For Owner offer type-ahead from values already in the repository.
- **Severity:** Low
- **Effort:** S
- **Type:** Layout

### UX-28 "+ New item…" dominates the toolbar
- **Screen / element:** 02, 03 — toolbar end.
- **Problem:** The largest filled primary element on the main screen is "+ New item…" (a split button whose ▾ looks like a select), so the eye goes there, not to the table or Save. Creating items is less frequent than reading and editing them.
- **Evidence:** 190 px wide filled blue button vs. neutral toolbar buttons.
- **Proposal:** Keep it primary but compact: label "New item", width fit to content, ▾ as a separated segment (border-inline-start `primaryText` at 30 % opacity). Expand-all/Collapse-all icons (⊞ ⊟) get tooltips "Expand all" / "Collapse all" and sit next to the search, as they act on the tree view.
- **Severity:** Low
- **Effort:** S
- **Type:** Visual

### UX-29 Fields dialog shows technical details first
- **Screen / element:** 06-fields-dialog.
- **Problem:** "key: status" lines in mono under each name, the file path `requirements/.reqman/schema.yaml` in the intro, and "Kind" values like "Choice (one value)" read like a config file; "Options (comma separated)" for a list field says "optional — empty allows any value".
- **Evidence:** Intro sentence with the YAML path; key lines under every row.
- **Proposal:** Intro: "Every item has these fields. Your changes reach the team with your next commit and push." (path in a tooltip on an ⓘ icon). Show "key" only on hover/focus of the row. Column "Kind" → "Type of value"; options "Choice (one value)" → "One of a list", "List (several values)" → "Several from a list", "Text" stays. Options placeholder: "Allowed values, separated by commas (empty = any value)".
- **Severity:** Low
- **Effort:** S
- **Type:** Wording

### UX-30 Settings: inline button in a status line, meaningless rows, colour-only dots
- **Screen / element:** 19-settings-environment-versions.
- **Problem:** "Check for updates" is a filled primary button squeezed into a sentence; "Theme — App theme" tells nothing; the status dots (green/grey) carry meaning by colour only. The filled blue "Back" is the strongest element of every settings page.
- **Evidence:** Row "Updates: Off (only the installed Windows app updates itself) [Check for updates]"; dot colours.
- **Proposal:** Updates row: text "Automatic updates: off in this copy (only the installed Windows app updates itself)" and the button below the text, secondary style. Theme row: "Theme: built-in" or "Theme: your file (theme.json)". Dots get a text state ("OK" / "Off" / "Missing") next to them. "Back" becomes a secondary button with ← icon ("Back to the project").
- **Severity:** Low
- **Effort:** S
- **Type:** Visual

### UX-31 Settings and guide text is small and long-lined
- **Screen / element:** 19–22 card descriptions; 23 guide navigation.

- **Evidence:** Descriptions under "Versions", "Report a problem", "Features", "Self-tests"; guide topic list.

### UX-32 Pull decision dialog: chosen side not visible, technical title
- **Screen / element:** 25-pull-decision-dialog.

- **Effort:** S

### UX-33 Diff highlights are asymmetric
- **Screen / element:** 12-changes-view diff.
- **Problem:** The old line is tinted as a whole while the new line marks only the added words, so a reader cannot see quickly what was replaced vs. added; colour is the only signal (red/green) for colour-blind users.
- **Evidence:** Line 5 old fully pink; line 5 new with "within 2 seconds" marked green.
- **Proposal:** Word-level marks on both sides (`diffOldMark` / `diffNewMark`), with removed words also struck through and added words underlined, so the change reads without colour. Line gutters show "−" / "+".

- **Effort:** S

### UX-34 Export dialog: disabled option reads as an error

- **Evidence:** Second radio greyed.

### UX-35 Dark mode: disabled primary looks enabled; selected row low contrast

### UX-36 Status bar hint is static and wastes the bar

Use the space for: "3 chosen" when several rows are selected, "Filtered: Status = Draft" with a ✕ when filters are active, and "Last pull: 10:42" at the end before the path. Path truncated in the middle with full path in a tooltip.

- **Effort:** S

## Open questions

1. **Translated field and type names in Arabic (UX-22).** Recommended: allow optional `label: { en, ar }` in
   `schema.yaml` and ship Arabic labels for the default fields. Alternative: keep schema names in one language chosen
   by the team (simpler, but mixed-language headers stay for Arabic users).
2. **"Commit and push" in one click (UX-18).** Recommended: offer it as the secondary part of a split button, with
   "Commit" staying the default, so review-minded teams are not pushed to share too early. Alternative: one
   "Commit and push" default button (fewer clicks, but harder to recover from a wrong commit).
3. **Rendered text before theme 3a (UX-08).** Recommended: show rendered Markdown when the Text field is not being
   edited, now, as a small step towards 3a. Alternative: wait for the full rich-text editor in 3a (no interim work,
   but the pilot team reads raw Markdown for several versions).
4. **Language and theme switches in the top bar (UX-13).** Recommended: move them to a Settings → Appearance page and
   keep them on the start screen. Alternative: keep them in the top bar but collapse each into one small icon menu.
5. **Default column order (UX-03).** Recommended: No. and Title first, ID later — closer to DOORS and Jama reading
   habits. Alternative: keep ID first for teams that quote IDs in reviews; either way the order stays user-adjustable.

## Decisions (owner, 3 Nov 2026)

All recommendations accepted: the 7 High findings and the 15 quick wins go into a **UI polish version** before the
pilot; open questions 1–5 as recommended (Arabic labels for fields and types in `schema.yaml`; "Commit and push" as the
secondary part of a split button; rendered Markdown when the Text field is not being edited; language and theme
switches move to Settings → Appearance and stay on the start screen; default column order No., Title, Type, Status,
Links, …, ID). The remaining findings (UX-11, 16, 19, 25–36) were listed to the owner for a choice. Note: UX-30's
"Back as a secondary button" conflicts with the owner's own request (0.14.4: Back blue) — the owner's request stands.
