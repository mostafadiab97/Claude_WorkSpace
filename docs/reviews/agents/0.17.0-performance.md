# Performance report — 0.17.0 (frozen commit 6d1cfb5)

Scope: the data-layer cost of the 0.17.0 document features on 10,005 and 50,000 generated items — the per-document
filter (`substr` on the path), the Incomplete filter, the document counts in every `repoInfo`, the "All documents"
order with a CASE expression, `outlineNumbers` per document, and the folder watch with many document folders. Method:
a new script, `/tmp/claude-0/perf-0.17/perf-qa-0.17.mjs` (kept outside the repo as asked; the builder may copy it to `tools/perf-qa-0.17.mjs` and change its imports to `../src/...`; data layer only: writes the items into N document folders by root
ancestor, indexes them, times each query as the median of 7 runs, 1 run for the very slow ones), plus plain SQLite
experiments on the generated cache files (in `/tmp/claude-0/perf-0.17`). Linux container, Node 22, SQLite 3.53. The
window (IPC, rendering) was not measured. Targets are the limits in `tests/perf.test.ts` (query < 150 ms at 10k,
< 300 ms at 50k) and the owner's 10k "< 15 ms" in `docs/TESTING.md`. No product file was changed.

Run (from the repo folder): `npx tsx /tmp/claude-0/perf-0.17/perf-qa-0.17.mjs <workdir> <count> <documents>`.

## Findings

| ID | file:line | severity | what is wrong (F = checked, I = likely) | suggested fix |
| --- | --- | --- | --- | --- |
| PERF-01 | `src/modules/index-cache/sqliteIndex.ts:386` | **High** | F: The Incomplete filter grows quadratically. With required fields set, the query takes **3.0 s at 10,005 items and 82–84 s at 50,000** (target 150 / 300 ms; 20× and about 280× over). `EXPLAIN QUERY PLAN` shows why: the `NOT EXISTS (SELECT 1 FROM item_fields x WHERE x.rid = i.rid AND x.field = ? …)` is answered through `item_fields_lookup (field=?)`, so for every item the engine walks all the rows of that field (about 10k–50k) and applies `trim()` to each. The cost is the same with or without a `document` filter, and with 0 matches. The query runs synchronously in the main process, so the whole app is frozen for that time, and the same query serves the export of the current filter. Only projects whose schema has a `required:` list pay this (otherwise the SQL is `0`). | Force the right index: `FROM item_fields x INDEXED BY item_fields_rid WHERE x.rid = i.rid …` — measured at 50k: **14,842 ms → 11 ms** (one type, one field). `i.rid NOT IN (SELECT rid FROM item_fields WHERE field = ? AND trim(value, …) <> '')` also works (17.6 ms). Add a perf test with `required` set to `tests/perf.test.ts` / `runDataBenchmark` (it has no Incomplete case, which is why the CI perf test did not see this). |
| PERF-02 | `src/modules/workspace/workspace.ts:128-133` | Medium | F: `documentsOf` runs one count query per document folder, each one a full scan of the items table (the `substr` filter cannot use an index), on every `repoInfo`. Cost grows with documents × items: 10k items: 2 documents 1.6 ms, 11 docs 6.6 ms, **1,001 docs 570 ms**; 50k items: 11 docs 29 ms, **501 docs 1.29 s**. `info()` is called from 13 places in the workspace module (open, refresh, every structure change). Few documents are the normal case (cheap), but a project with one folder per chapter will feel it on every refresh. | One query for all documents: `SELECT CASE WHEN instr(path,'/')>0 THEN substr(path,1,instr(path,'/')-1) ELSE '' END d, COUNT(*) FROM items GROUP BY d` — measured at 50k: **12 ms** whatever the number of documents. Folders without items still come from `documentFolders` with count 0. |
| PERF-03 | `src/modules/index-cache/sqliteIndex.ts:399-400` | Low | F: The per-document filter `substr(i.path, 1, length(?) + 1) = ? \|\| '/'` scans every row. Cost is acceptable alone: count of one document 0.5–0.6 ms at 10k, 2.5 ms at 50k, first page of one document 2–9 ms at 10k and 12–51 ms at 50k, independent of the number of documents. It is the reason for PERF-02 and it makes "one document, top level, order" 51 ms at 50k (see table below). | A range test uses the existing unique index on `path`: `i.path >= ? \|\| '/' AND i.path < ? \|\| '0'` ('0' is the character after '/'). Count of a document at 50k: **2.4 ms → 0.1 ms**. Needs care with LIKE-free escaping only (no wildcards involved). Not urgent. |
| PERF-04 | `src/modules/index-cache/sqliteIndex.ts:445` | Low | F: The CASE prefix in "All documents, top level, order" forces a sort of all top-level rows instead of reading them in index order. Measured directly in SQLite at 50k (20,000 top-level rows): first page 27.0 ms with CASE vs 25.2 ms without; page at offset 5000 **62 ms vs 27 ms** (2.3×). Through the app query: first page 6 ms (10k) → 32 ms (50k); offset 5000 17 ms → 100–105 ms. Within the targets (< 300 ms at 50k) but it grows linearly. Note the base sort `i.ord IS NULL, i.ord` already prevents use of `items_parent (parent, ord)`, so the table is sorted even without the CASE. | Optional: store the document in its own column (`doc TEXT`, filled in `insertItem`, `FORMAT_VERSION` bump) with an index `(doc, parent, ord)`; this also makes PERF-02/03 trivial and removes the CASE. Only worth it if 50k projects with many top-level items are a real case. |
| PERF-05 | `src/modules/workspace/structure.ts:70`, `workspace.ts:85-88` | Low | F: `outlineNumbers` with per-document trees stays linear: 10k items 13–19 ms, 50k items 71–86 ms; with `structure()` (reading all rows from SQLite) 27–38 ms at 10k and 196–265 ms at 50k, nearly the same for 1, 10 or 1,000 documents (rows are listed once; roots per document are a `Set`). It is cached by index revision, so it is paid after each write, not on each query. About 0.2–0.27 s after every write on a 50k project. | None needed for 0.17. If it ever hurts: compute only the changed document (the document field is already in `structure()`). |
| PERF-06 | `src/modules/workspace/watcher.ts:36-97`, `workspace.ts:101-108` | Low | F: The folder watch with many documents is cheap: start 3 ms (2 folders), 8.7 ms (1,001 folders at 10k), 21.8 ms (501 folders at 50k); close 0.2–7.6 ms; `documentFolders()` (called on every `rewatch`, that is every refresh) 0.0 ms (2 folders) to 0.5 ms (1,001 folders). Linux inotify created 1,001 watches without failure. I: on Windows each watch is a directory handle, and a Git action that removes folders needs the watch closed (already done by `paused`); the watch count has no upper bound — 1,000+ document folders is not a realistic pilot, but a failing `watch()` already falls back to `all` (full check), so the failure is safe. | None. Optionally watch the requirements folder recursively on Windows/macOS (`recursive: true`) instead of one watcher per document. |
| PERF-07 | `tests/perf.test.ts`, `src/modules/sample-data/benchmark.ts:50-62` | Medium | F: The perf test list has no case for the 0.17 queries (document filter, Incomplete with required fields, All-documents order, documents count), and the generated data has no document folders (one `items` document). PERF-01 would have failed the 10k limit (3 s vs 150 ms) immediately. | Add to `runDataBenchmark`: `{ incomplete: true, required }`, `{ document, sort: order }`, `{ parent: null, sort: order }` and `documentsOf`; spread the generated items over some document folders (e.g. 10). The script `/tmp/claude-0/perf-0.17/perf-qa-0.17.mjs` shows how. |

Note on the "Incomplete + top-level order" row: with `parent: null` the query is fast because only top-level items are
tested (`required` is applied to fewer rows and the correlated query then runs on them); it is not a path the Incomplete
toolbar filter normally uses (the toolbar sends no parent filter when a link filter is set — I, not checked in the window).

Per-version comparison: earlier measurements in `docs/TESTING.md` (10k query < 15 ms on the owner's PC, the suspect
filter 0.3 s with window) are unchanged by 0.17 — the reference rows above (suspect 9.6 ms, type 2.9 ms at 10k) match
them; nothing that existed before 0.17 became slower. The 50k queries not touched by 0.17 are also within targets.

## Questions for the owner

None — the findings are technical.

## Checked, nothing found

- First index and re-sync with documents: 10k 3.1 s / 0.23 s, 50k 15 s / 1.1 s, equal for 10 and 500–1,000 document folders (no growth with the number of folders).
- Writing items into many folders (2.4–2.7 s at 10k, 12.5–13.9 s at 50k): no growth with the number of folders.
- Items-per-document filters other than the Incomplete one (document + order, document + ID sort): all within target at 10k and 50k.
- Folder watch start/stop and `documentFolders()` with 1,001 folders: cheap, no watch failure on Linux (Windows handles were not measured).
- `outlineNumbers` with many documents: linear, same cost for 10 or 1,000 documents.
- Not measured: the window (IPC and rendering of the document bar with many documents), the Windows file watch, the export of the Incomplete filter (it uses the same SQL, so PERF-01 applies), Defender effects on the owner's PC.

## Outcome (builder, 8 Nov 2026)

- PERF-01 fixed: `INDEXED BY item_fields_rid` in the Incomplete SQL — 10k: 3.0 s → 13 ms (CI perf test now has the case).
- PERF-02 fixed: `index.documentCounts()` — one GROUP BY instead of a count per document.
- PERF-03 fixed: the document filter is a range on the path index (`"<doc>/" ≤ path < "<doc>0"`).
- PERF-07 fixed: `runDataBenchmark` has the document, All-documents order, Incomplete and per-document count cases.
- PERF-04/05/06: no change (within the targets); a `doc` column stays an option if 50k projects need it.
