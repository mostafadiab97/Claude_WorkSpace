# Security review — 0.18.0 (commit 2653a2a, changes since v0.17.2)

Scope: the new Git commands (baseline tags, pushing tag refspecs, history `log --grep` from the search box, branch at a
commit, `git config --local` writes), the six new window calls and their checks in `validate.ts`, "renew copy ID",
discard now deleting empty folders, the updater's fallback through GitHub's API with `setFeedURL` to a generic address,
and the CI changes made between v0.17.0 and v0.17.2 that no security review has seen yet (`tools/ci-electron.mjs`, the
gh downloads and `GH_TOKEN` in both workflows). Evidence: reading the diffs, two small Git experiments in a scratch
repository (results quoted), and a check of `node_modules/electron/checksums.json`. Findings from earlier reports
(0.17.0, whole-project) are not repeated. Words used: *install script* = code a library runs automatically during
`npm ci`; *refspec* = the "local:remote" name pair `git push` sends; *annotated tag* = a Git label with a message.

| ID | file:line | severity | what is wrong (F = checked, I = likely) | suggested fix |
| --- | --- | --- | --- | --- |
| SEC-18-01 | .github/workflows/build.yml:54; release.yml:70 | Medium | **F** The step "Install (retried)" sets `GH_TOKEN: ${{ github.token }}` for the whole step, so `npm ci` runs every library's install script with a token that has `contents: write` (job level). A single hijacked library version could use it to create or change a GitHub release, which is the auto-update feed of every installed copy. Before 0.17.2 `npm ci` ran without any token (I: impact; F: env and permission lines). | Give the token only to the Electron download: run `npm ci` in a step without `GH_TOKEN`, then a separate step `node tools/ci-electron.mjs` with `GH_TOKEN`. Better still, that download needs only read access: give the job `contents: read` and grant `write` only to the release step (see the open SEC-03). |
| SEC-18-02 | tools/ci-electron.mjs:26, 36-39 | Low | **F** The Electron zip is checked against `SHASUMS256.txt` downloaded from the **same** release. That catches a broken download, not a replaced file (whoever can swap one can swap both). The Electron package already contains `node_modules/electron/checksums.json`, pinned by `package-lock.json`'s integrity hash; it lists `electron-v45.0.0-win32-x64.zip` (checked with a one-line `node -e` script). | Read the expected SHA-256 from `node_modules/electron/checksums.json` (it is what Electron's own installer uses) and drop the `SHASUMS256.txt` download. |
| SEC-18-03 | src/modules/git-adapter/systemGit.ts:433-442 (`baselines`) | Low | **F** The tag message (`%(contents)`) is printed raw and records are split on `\x1e`. A baseline tag whose message contains `\x1e` and `\x1f` adds fake entries (any name, commit, author, date) to the Baselines list. Test: one tag `baseline/real` with a crafted message was parsed as two baselines `['real', 'fake-release']`. Anyone who can push tags to the shared remote can plant one, and the list is what users trust as "released state". | Read the names and commits in one call (ref names cannot contain control characters), then read each message separately (`git cat-file tag <oid>` or `for-each-ref --format=%(contents) <ref>` per name). Or keep the call but drop every parsed entry whose name/commit is not in the first list. |
| SEC-18-04 | src/main/validate.ts:287-292 (`commitRef`); baselines.ts:16 | Low | **F** A commit ID of 7–39 hex digits is accepted, but Git resolves a short hex to a **tag or branch of the same name** first. Test: a tag named like commit A's short ID, pointing at commit B: `git rev-parse <short>^{commit}` returned B (only a warning "refname is ambiguous"). So snapshot, baseline or branch-at could act on another commit than the one shown. Today the window sends full 40-digit IDs (`%H`), so this is about robustness (I). Side note: SHA-256 repositories (64 digits) are refused. | Accept only full IDs (`^[0-9a-f]{40}$\|^[0-9a-f]{64}$`), or resolve once with `rev-parse --verify --end-of-options <x>^{commit}` and use the result only if it starts with `<x>`. |
| SEC-18-05 | systemGit.ts:470-474 (`history` search by ID); baselines.ts:36-49; gitOps.ts:238-252 | Low | **I** Searching for a commit ID uses `rev-parse` on the whole repository, so it also finds commits that are not on the current branch, including one the user removed with "Undo commit" (it stays in Git for weeks). A baseline made there is pushed on the next Push without asking. Pushing a tag also sends that commit and all its history, which may hold text the user meant to remove. | Allow a baseline only at a commit of the current branch (`git merge-base --is-ancestor <commit> HEAD`), and limit the ID search the same way. |
| SEC-18-06 | gitOps.ts:248-252; systemGit.ts:455-468 | Low | **I** The tag push is one command for all waiting baselines. If one name already exists on the remote (a colleague made the same name), Git refuses it, the command fails, and the waiting list is kept, so **every later Push** reports a failure, even though the branch went through. Also `setPendingBaselines` first removes the whole list, then adds names one by one: if it stops halfway, waiting baselines are forgotten (never pushed, no message). | After a failed tag push, ask the remote which tags arrived (`git ls-remote --tags <remote> refs/tags/baseline/*`), drop those from the list, and name the clashing tag in the message. Write the list with one `git config` call per name only after checking, or keep it in a single value. |
| SEC-18-07 | validate.ts:296 (`baselineRequest`) | Low | **I** Baseline names may contain invisible and text-direction characters (Unicode class Cf, e.g. right-to-left override). Git's `check-ref-format` accepts them. Baselines go to the shared remote, so a name can be made to look like another one (e.g. a fake "v1.0"). This is the same kind of problem as SEC-17-04, in a new place. | Refuse `\p{Cf}` (and keep the current checks). |
| SEC-18-08 | src/modules/updater/githubUpdater.ts:96 | Low | **F** The fallback builds `https://github.com/${owner}/${repo}/releases/download/v${target.version}` from the API's `tag_name` without checking its form, and without encoding `owner`/`repo` (the API address two lines above does encode them). The source is the owner's own release list, so this is about robustness. The downloaded installer is still checked against `latest.yml`'s SHA-512 (F). | Use the fallback only if `target.version` matches `^\d+\.\d+\.\d+$`; use `encodeURIComponent` for all three parts. |
| SEC-18-09 | baselines.ts:72-77; systemGit.ts:60-90 (`readBlobs`) | Low | **I** "Look at this version" reads **every** item file of any commit fully into memory (no size limit in `readBlobs`), then parses its YAML. A pushed commit with a few huge `.md` files can make the app run out of memory when someone opens that version. This is the history version of SEC-17-03. | Ask for the sizes first (`git cat-file --batch-check`) and skip files over 1 MB (show them as "too big"). |

## Questions for the owner

- Should a baseline only be allowed on the current branch's own commits (SEC-18-05)? Recommended: **yes**. The history
  list only shows those commits anyway; the search by ID is the only way to reach others.

## Checked, nothing found

- New window calls: `renewCopyId`, `listBaselines`, `createBaseline`, `getHistory`, `getSnapshot`, `createBranchAt`
  each check their input in `ipc.ts` with `validate.ts` (ID, commit ID, name/note/message lengths, `skip` number range).
- Git commands are argument arrays, never a shell string. The tag name always starts with `baseline/` (it can never be
  read as an option). `createBranchAt` puts `--` before the name, and the name is checked with
  `check-ref-format --branch`. The search text goes in as one `--grep=` argument with `--fixed-strings`, and only
  hex text reaches `rev-parse`. Refspecs start with `refs/` (a leading `+` cannot force a push). Nothing is force-pushed.
- `git config` writes use `--local` only, with names already checked (no line breaks, backslashes or control characters).
- Discard now deletes folders, but only empty ancestors of the deleted files. It stays inside the repository (the paths
  come from Git's status and must be in the change list), and `rmdir` refuses folders that are not empty. On Windows a
  linked folder (junction) loses only the link, not the folder it points to.
- `renewCopyId`: the ID is checked, the paths come from the index, the new file is written before the copy is removed,
  and nothing outside the project folder is touched.
- Updater fallback: HTTPS to api.github.com/github.com only, the feed is reset to the normal one before every check,
  only one fallback per check, and the SHA-512 check of the installer is unchanged.
- Workflows: actions still pinned by commit ID; the acceptance run's push still skipped for pull requests; gh downloads
  are fixed versions; Windows' `tar` refuses `..` paths in the zip. gitleaks is still run without a checksum
  (SEC-15, still open), and `contents: write` still applies to pull-request runs (SEC-03, still open).
- Secrets: no token or key in the lines added since v0.17.0 (searched for GitHub, AWS, Slack and private-key patterns:
  0 hits); gitleaks was not available here and runs in CI.
- Electron settings, preload, libraries: no change since v0.17.2 (`package.json`, `package-lock.json`, `src/main/index.ts`,
  `src/preload` unchanged).
