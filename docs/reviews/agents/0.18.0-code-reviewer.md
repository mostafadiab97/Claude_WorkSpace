# Code review — 0.18.0 (frozen commit 2653a2a, changes since v0.17.2)

Scope: baselines, history and snapshot (`workspace/baselines.ts`, the new `git-adapter` calls, the baseline part of
Push in `gitOps.ts`, the new `validate.ts`/`ipc.ts` entries), "Give the copy a new ID" (`renewCopyId`) and the new
cross-document top-level SQL in `sqliteIndex.ts`, Discard removing empty folders, the updater's API fallback, the new
dialogs (HistoryDialog, SnapshotDialog), the incomplete-mark and document-bar changes, and the docs for these areas.
Line numbers are those of commit 2653a2a. `npm run check` on the current working tree: types and lint pass; 7 tests
fail, all in the QA file `tests/qa-0.18.0-baselines-history.test.ts` (QA-01, 02, 04, 06, 10, 11, 13). Note: the
working tree already holds uncommitted builder fixes (pushBaselines one by one, history on an empty repository,
Escape in the form…). Findings that those fixes already cover are marked "(being fixed)".

Terms: *tag* = a named pointer to a commit that Git can send to the remote; *pending* = a baseline made here that has
not been pushed yet (stored in the repository's own Git config, `reqochet.baselineToPush`).

## Questions for the owner

1. Two people make a baseline with the same name, and the second Push is refused for that name. Should reqochet
   (a) ask for a new name and rename the local baseline (recommended), or (b) only say so and keep the local one
   as it is?
2. Your copied file was ambiguous (both files already in Git, or no Git). Should reqochet (a) ask you which file
   keeps the ID (recommended), or (b) keep guessing by the newest file?
3. When several copied files form a hierarchy, should "Give the copy a new ID" (a) renew all copies of that
   document at once and keep their hierarchy (recommended), or (b) one file at a time as now?

## Checked, nothing found

- Window calls: the 6 new methods each have a `ReqochetApi` method, a `Channels` entry and an `ipc.ts` handler with `validate.ts` checks (commit IDs are hex only, never option-like).
- Workspace queue: `createBaseline`, `createBranchAt` and `renewCopyId` are queued; `baselines.create` calls the inner `gitOps.commit`, not the queued one, so it does not wait for itself; read-only calls (`listBaselines`, `getHistory`, `getSnapshot`) are correctly left unqueued.
- Never force-push: tag refspecs have no `+`; the branch push is unchanged; tidying before a baselines-only Push changes nothing (no commits ahead = no changed groups).
- SQLite: no table layout changed (only a query and `pathsOf`), so `FORMAT_VERSION` correctly stays 4; the correlated subquery uses the `items_id` index.
- Byte-wise order: the snapshot sorts order keys with `<`/`>` and puts items without a key last, like the index (`ord IS NULL, ord`).
- Discard removing empty folders: stops at the first non-empty folder and never at the repository root; a document made with **New document** keeps its `.gitkeep`, so its folder stays; Discard runs with the watcher paused.
- Module boundaries: `baselines.ts` imports only module entries (`../items`, `../git-adapter`) and its own folder; the renderer uses only `window.reqochet` and shared types.
- Updater fallback: only release assets on `https://github.com/` are used, drafts and pre-releases are skipped, and the feed goes back to the GitHub provider on the next check; holds (version kept on purpose) are respected.
- Theme and texts in the new dialogs: no colour literals; every word comes from `T` (the two symbols ✕ and → excepted, see CR18-15); the Escape handling of SnapshotDialog stops the event before it reaches HistoryDialog.
